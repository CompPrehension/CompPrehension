# architecture-tests

Модуль без продакшн-кода. В нём живут ArchUnit-правила — исполняемое описание того,
какой слой что имеет право видеть. Запускается вместе с обычными тестами (`mvn verify`),
падает в CI при нарушении.

## Зачем

Соглашения в вики не работают: их забывают, а ревью пропускает. Правило, которое ломает
сборку, работает. Основная цель набора — не «красота слоёв», а конкретная вещь: не дать
JPA-сущностям и ленивым связям утекать за границу транзакции, потому что именно оттуда
берутся скрытые N+1.

## Как это устроено

Правила обёрнуты в `FreezingArchRule`. При первом запуске ArchUnit записал все нарушения,
которые в коде уже были, в каталог `archunit-violations/` — это **baseline**. Дальше:

* новое нарушение → сборка падает;
* существующее нарушение → сборка проходит, счётчик не растёт;
* нарушение починили → ArchUnit сам вычёркивает его из baseline, вернуть его назад уже нельзя.

То есть `archunit-violations/` — это измеренный техдолг по слоям, который может только
уменьшаться. Каталог коммитится в git; уменьшение файлов в нём — нормальная часть диффа
рефакторинга, увеличение — повод для вопроса на ревью.

Текущее состояние baseline:

| нарушений | правило |
|----:|---|
| 44 | JPA entities should not appear in controllers |
| 33 | domain contracts should not expose JPA entities |
| 11 | repositories should not depend on web DTOs |
| 5 | business logic should not depend on the web stack |
| 2 | dependencies should be injected via constructor, not into fields |
| 1 | @ManyToOne and @OneToOne associations should declare fetch = LAZY |

Остальные семь правил соблюдаются полностью и **не обёрнуты в `FreezingArchRule`** — они
строгие. Это и есть договорённость: заморозка означает «здесь есть долг», её отсутствие —
«здесь чисто, ломать нельзя». Когда очередное правило доходит до нуля, снимайте с него
обёртку и удаляйте его файл из `archunit-violations/`.

### Про контракты предметного ядра

Правило `domain contracts should not expose JPA entities` смотрит на интерфейсы
`Domain`, `Backend`, `AbstractStrategy` и типы, объявленные внутри них. Проверяются только
сигнатуры — типы параметров, возвращаемые типы и поля, с разворачиванием дженериков
(`List<ResponseEntity>` — такое же нарушение, как `ResponseEntity`). Тела default-методов
не проверяются: это реализация, а не контракт.

Сущность в сигнатуре означает, что реализация обязана получить объект, живущий в сессии
Hibernate, а вызывающий — открыть транзакцию. `Backend` показывает, что так можно не
делать: он параметризован `BackendInput`/`BackendOutput` и о персистентности не знает,
поэтому в baseline его нет вовсе. Весь долг сосредоточен в `Domain` (8 типов сущностей)
и `AbstractStrategy` (3).

## Запуск

```
mvn -DskipTests install && mvn -pl modules/architecture-tests test
```

Первая команда обязательна: правила читают не classpath, а `modules/*/target/classes`
напрямую — `server` и `background-server` пакуются spring-boot-плагином в fat-jar, где
классы лежат под `BOOT-INF/classes/` и по имени пакета не находятся. Если положиться на
classpath, правила про контроллеры молча проверяют пустое множество и всегда зелёные.
От повторения этой ситуации защищает `ImportCoverageTest`, а от несобранного модуля —
явная ошибка в `ProjectClassesLocationProvider`.

## Что делать, когда правило упало

1. **Обычный случай — почините код.** Сообщение называет класс, поле и строку.
2. Правило действительно неприменимо в этом месте — сузьте его условие в тесте,
   осознанно и с комментарием, почему исключение оправдано.
3. Заводите новое правило на легаси-код — оберните в `FreezingArchRule.freeze(...)`,
   запустите один раз, закоммитьте появившийся файл baseline вместе с правилом.

Чего делать **нельзя**: ставить `freeze.refreeze=true` в `archunit.properties` и коммитить.
Это перезаписывает baseline текущим состоянием кода и стирает весь накопленный техдолг
одним движением, после чего правила снова ничего не значат.
