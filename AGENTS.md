# CompPrehension

CompPrehension — мультидоменная интеллектуальная обучающая система. Она расширяется по трём независимым осям:
- **домены** — предметная область: понятия, законы, генерация вопросов, объяснение ошибок;
- **стратегии** — какой вопрос дать следующим и как оценить прогресс студента;
- **ризонеры** — как по модели области вывести правильный ответ и найти нарушенные законы.

Ядро (упражнения, попытки, банк вопросов, интеграция с LMS) от конкретной области не зависит.
Java 25, Spring Boot, MySQL + Liquibase, фронтенд на React + Vite.

## Модули

| модуль | что внутри | зависит от |
|---|---|---|
| `common` | утилиты без Spring | — |
| `core-api` | контракты: модели данных `data..`, интерфейсы сервисов `services`, предметное ядро `businesslogic` (`Domain`, `Backend`, стратегии), web-DTO `frontend.dto`, интерфейсы `mappers` | `common` |
| `core` | реализация: `entities`, `repositories.entity` (Spring Data), `repositories.data`, `repositories.mappers`, `services`, `frontend` (+ `frontend.mappers`) | `core-api` |
| `backends` | ризонеры (Jena, деревья решений) | `core-api` |
| `domains` | предметные области и генерация наводящих вопросов | `core-api`, `backends` |
| `strategies`, `bkt` | стратегии подбора вопросов | `core-api`, … |
| `server` | Spring Boot: `controllers`, конфигурация, фронтенд `src/main/js`, миграции Liquibase | всё |
| `background-server` | фоновые задачи (генерация вопросов) | всё |
| `expr-domain-question-generator` | генератор вопросов домена выражений | `core`, `domains` |
| `external-api` | интеграция с Moodle | — |
| `architecture-tests` | правила ArchUnit на весь проект | всё |

`core-api` не зависит от Spring, JPA и web-стека. Домены, бэкенды и стратегии видят только `core-api`.

## Слои и направление вызовов

```
controller (server)
  → *FrontendService          core/frontend         — сценарий запроса, data → DTO через frontend.mappers
  → *DataService              core-api/services     — интерфейс; реализация в core/services
  → *DataRepository           core/repositories/data — entity ↔ data через repositories.mappers
  → Spring Data репозиторий   core/repositories/entity
  → JPA-сущность              core/entities
```

Бизнес-логика (`Domain`, `Backend`, стратегии) вызывается из сервисов и получает только модели данных.

Кто за что отвечает:
- JPA-сущности не выходят за `repositories.data`. Spring Data репозитории используются только оттуда.
- Преобразования entity ↔ data делают только мапперы `repositories.mappers`; data → DTO — только мапперы
  `frontend.mappers`. Web-DTO строят только мапперы.
- Маппер — `@Component`, пакетный, реализует `Mapper`/`UpdateMapper`, ничего не загружает, без статических методов.
- Репозитории не знают о web-DTO. Сервисы не знают о контроллерах и HTTP.
- Модели данных в `data..` по возможности неизменяемые: `record`, Lombok `@Value`, sealed-иерархии
  для вариантов (см. правило 4 ниже).

Большая часть этого проверяется ArchUnit-тестами в `modules/architecture-tests` — они и есть источник истины.
Правила намеренно жёсткие, местами гайки сильно закручены. Если есть веские основания пересмотреть правило,
это обсуждаемо — но ослаблять или отключать правила можно только после согласования.

## Правила кода

1. Код простой и понятный, работает очевидным образом.
2. Новые классы — только по объективной причине. Но один класс не должен использоваться по-разному
   с разными наполнениями (поле то значит одно, то другое; часть полей игнорируется в одном из режимов).
3. Имена методов содержат глагол. Исключения: методы рекордов, геттеры и подобное; `to*` допустимы.
   Производное значение неизменяемого объекта считается один раз в конструкторе и отдаётся геттером.
4. По возможности классы неизменяемые — особенно когда это ничего не стоит (`record`, `@Value`, `final`-поля).
   Но не тогда, когда это становится неудобно или требует лишних аллокаций (копирование на каждое изменение).
5. Меньше аллокаций: не пересоздавать коллекции на каждый вызов, не создавать объект ради одного сравнения —
   статическое поле или константа.
6. Меньше обращений к БД — но не ценой усложнения кода и не ценой нарушения слоёв.
7. Никаких статических методов в интерфейсах.
8. В новом коде nullability указывается явно: `org.jetbrains.annotations.@NotNull`/`@Nullable` на параметрах,
   возвращаемых значениях и полях. Существующий код ради этого не трогать.
9. Код объясняет себя именами и структурой: комментарии и javadoc, пересказывающие код, не нужны.
   Места, которые работают неочевидно и требуют пристального внимания, комментировать можно и нужно.
   Чужие существующие комментарии не трогать.
10. Новое поведение и изменения логики закрепляются тестом на уровне сценария — новым или дополнением
    существующего.
11. Тест закрепляет поведение системы, а не устройство кода. Перед тестом сформулировать одной фразой, какое
    правило или сценарий он фиксирует и что сломается для пользователя, если он упадёт. Если фраза пересказывает
    метод («метод X возвращает Y») — тест не нужен.
    - Нужны: бизнес-сценарии через точку входа (фронтенд-сервис, контроллер, домен); бизнес-правила
      и граничные случаи; регрессионный тест на каждый исправленный баг.
    - Не нужны: тесты делегирования и тонких сервисов/репозиториев без своей логики; повтор одного поведения
      на нескольких слоях — оно проверяется там, где имеет смысл для пользователя.
    - Образцы: `LtiControllerTest`, `LtiDeepLinkingControllerAuthorizationTest`,
      `ProgrammingLanguageExpressionDTDomainSupplementaryQuestionsTest`.
12. Тесты: на каждый тестовый метод один короткий `/** … */` на русском и маркеры
    `// Arrange.` / `// Act.` / `// Assert.`. Если действие и проверку сложно, неудобно или неэстетично
    разделять (`assertThrows`, серия однотипных проверок), допустим общий маркер `// Act & Assert.`. Имя и javadoc описывают сценарий на языке предметной области,
    а не имя метода. Другие комментарии — только к неочевидным местам (правило 9).
13. Тесты по возможности переиспользуют существующую инфраструктуру: `AbstractIntegrationTest`, `TestData`,
    `DomainFixtures`, контракты доменов (`*Contract`), `RandomObjects`. Новый хелпер или базовый класс —
    только если в существующих нужного нет.
14. Тесты простые и прозрачные: без скрытого поведения под капотом. Всё, от чего зависит проверка, видно
    в самом тесте — никаких неявных настроек в базовых классах, `@BeforeEach` или фикстурах, от которых
    результат зависит незаметно для читателя.

## Как работать

- Перед изменениями коротко перечислить шаги плана, потом делать.
- Для всего, что больше локального фикса, сначала предложить решение: какой слой отвечает, какие контракты
  меняются, какие классы и методы появляются и зачем. Код — после согласования.
- Решение — фундаментальное, корректное и продуманное, а не быстрый костыль.
- Изменений — как можно меньше, но качество решения важнее их количества.
- Не отвлекаться на попутно найденные ошибки: не исправлять и не зацикливаться на них, а вынести отдельным
  пунктом в ответе с предложением.
- Не коммитить без команды.

## Dev-база

Для отладки можно читать dev-базу MySQL в любой момент. Доступы — переменные `MYSQL_*` в
`.env/compprehension-env.env`. Любые изменения в БД (`INSERT`/`UPDATE`/`DELETE`, DDL, миграции руками) —
только после согласования. Остальные секреты из этого файла не использовать.

## Сборка и проверка

```bash
mvn install -DskipTests                        # собрать всё
mvn test -pl modules/domains                   # тесты модуля
mvn test -pl modules/architecture-tests        # архитектурные правила, после install
```

- После любых изменений Java-кода прогонять `architecture-tests` и тесты затронутых модулей.
- Серверные тесты — интеграционные на Testcontainers, наследуются от `AbstractIntegrationTest`.
- Тесты доменов работают на реальных вопросах из банка (`DomainFixtures`, bank-JSON).
- Миграции: Liquibase, `modules/server/src/main/resources/db/changelog/YYYY-MM-DD/YYYY-MM-DD-NN-changelog.xml`,
  подключаются в `db.changelog-master.xml`, у каждого changeSet есть rollback.
- Фронтенд: `cd modules/server && npm run build` (lint + typecheck + сборка). Собранный бандл лежит
  в `src/main/resources/static` и коммитится вместе с исходниками.
